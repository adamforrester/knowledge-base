Source: Nathan Curtis, on the specs architecture as a hub of design intent across Figma, prototypes and code libraries (nathanacurtis.substack.com, 2026; "Spec-driven UI component development current state, August 2026"). Shared by the owner on 2026-10-14 as text plus five figures: the hub diagram (Figma ⇄ specs, specs → prototype, prototype → specs greyed; specs → React/Android/iOS via scripts and agents), "Consuming specs", "Versions" (latest/ with components, tokens, assets {fonts, icons, images, marks}, changelog, release_notes.md; plus 1.1.0, 1.0.1, 1.0.0), "From specs to prototypes" (card.css, card.contract.ts, card.stories.ts, card.generated.tsx) and "From specs to Figma" (a render command through a localhost bridge and a cache: 808 components, 77 styles, 300 variables, 56 icons; a badge rendered in 1.2s). Condensed from the shared text, with key sentences kept verbatim:

- Specs serve as the hub of design intent: "a single place where a design system records, evolves, projects, and synchronizes expressions of design intent ... It's a place that normalizes, synchronizes, and versions the intent expressed across the many origins-of-truth."
- Generated vs authored: "We favor generated over authored, and build tools that arc specs towards more generated outputs over time." Generated: api (names, props, elements), variants (layered rules: styles, tokens, prop bindings, slots, composition, layout), examples. Authored supplemental requirements: accessibility, behavior, configurations (discriminated unions, prop relationships), layout, motion. They are stored as files like configurations.md or card.accessibility.android.md, formatted with MUST/SHOULD/COULD, and authored by designers with agents and skills via pull requests.
- "Notwithstanding the considerable Figma motion tools released at Config 2026, designers continue to express motion requirements via a combination of prototypes and supplemental requirements for now."
- Foundations: tokens, fonts, icons, images, marks; taxonomies vary by client.
- Four edges: Figma to specs (plugin; REST API commands scanning READY_FOR_DEV; bridge), specs to Figma, specs to prototype code, prototype code to specs. "Great care has been put into how multiple paths produce 'byte-equivalent' (identical) specs whether from the Figma Plugin API or Rest API."
- Specs to Figma: "A specs render command leverages a bridge and a cache of system data to build a Figma asset from specs in complete detail: >50 style properties, props, tokens, Figma styles, prop bindings across variants, layout, and slots including default content." "Sure, agents could do this. Yet, inference comes with costs and risks ... The solitary render script is deterministic, demonstrated through 'round trips' (specs to Figma to specs) that prove specs remain byte-identical."
- Specs to prototypes: a transform command scripts CSS, a TypeScript contract, a React component scaffold and Storybook stories, using Figma authoring conventions for states and roles. Not for production, but a starting point for a prototyping kit.
- Prototypes to specs: early. Scaffolded code separates spec-worthy decisions (generated.css) from extensions.css and overrides.css.
- Versions: "Each version is accompanied by change logs, change sets, and skill-derived release notes ... When specs can be validated against an explicit schema, you remove all doubt about what changes are major/breaking, minor or patch fixes." Change or remove a prop: breaking. Add an anatomy element: minor. Bind a different token in a variant: patch.
- Schema plus content forms a contract. ADRs (metadata, context, problem, alternatives, decision, consequences, other concerns) evolve the schema, tools and models, authored with skills and LLMs; visions organize many ADRs.
- Analysis: an analyze command auto-generates reports every release: token and styling usage, props models, dependencies and keys. "Where is the text-tertiary token used across components and elements? How do options available for state vary across components? If I change the API of the icon component, what components are impacted?"
- Consuming specs: engineers build cross-platform factories (CSS, contracts, React TSX), per-platform skills and workflows, learning and testing capabilities. Engineers originate intent upstream too. Specs inform docs "some, but not much": how-to-use docs come from implementations.
- Open questions: designers in prototypes instead of Figma? Transpiling intent across code? One reference implementation or peers? "Will AI just do it?"
